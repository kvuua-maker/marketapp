# Архітектура MarketApp

## Принципи

1. **Нуль ручних дій.** Немає адмінки, немає кнопок «оновити». Синк, ціни, категорії та
   маршрутизація замовлень — це фонові процеси.
2. **Нуль залежностей на сервері.** `node:http`, `node:sqlite`, `fetch` — нічого не треба
   встановлювати, CI стартує за секунди, немає supply-chain ризику.
3. **Постачальник — це плагін.** Уся специфіка (формат, авторизація, ліміти) живе в адаптері.
4. **Вітрина ніколи не падає через ШІ.** Якщо DeepSeek недоступний — працює детермінований
   fallback, товари все одно публікуються.

## Потік даних

### 1. Синхронізація
`startScheduler()` запускає `runAllSyncs()` при старті (якщо останній синк старіший за
`SYNC_STALE_AFTER_MINUTES`) і далі кожні `SYNC_INTERVAL_MINUTES`. Один синк за раз,
без накладань.

Кожен адаптер віддає потік нормалізованих товарів:

```js
{
  externalId, title, description, imageUrl, images[],
  costCents, currency, stock, categoryRaw, productUrl, vendor, attributes[]
}
```

`aveopt.js` читає публічний WooCommerce Store API (пагінація по 100, retry/backoff).
`lugi.js` реалізує токен-авторизацію і курсорну пагінацію з публічних прикладів LUGI.
`zakupus.js` парсить XML власним парсером (CDATA, вкладені HTML, кілька `<picture>`).

### 2. AI-контролер
Для кожного товару:

1. **Валідація** — немає фото або опис коротший за 40 символів → `product_rejections`.
2. **Кеш** — хеш `title+description+categoryRaw`; якщо є в `ai_cache`, модель не викликається.
3. **DeepSeek** (батчами по 12) — українська назва, короткий опис, одна з 22 канонічних
   категорій. Відповідь перевіряється і приводиться до канону (`coerceCategory`).
4. **Ціна** — `retailPrice(costCents, margin)`; округлення `x9`, захист «не нижче собівартості».

Результат пишеться в `products` однією транзакцією на батч.

### 3. Замовлення
`POST /v1/orders`:

1. Валідація отримувача (ПІБ, телефон у форматі `+380…`, місто, відділення).
2. Перевірка наявності та залишків.
3. Групування позицій за `supplier_id`.
4. Для кожного постачальника — `adapter.placeOrder()`.
   Якщо API немає або він упав — лист у `outbox` (післяплата, адреса НП, склад замовлення).
5. Статус `routed` (API) або `routed_email` (лист), позиції отримують власний статус.

### 4. Доставка листів
`deliverOutbox()` викликається після кожного синку. `EMAIL_PROVIDER=outbox` — листи
лишаються в БД (безпечний дефолт), `resend` — реальна відправка через HTTP API.

## Схема БД

| Таблиця | Призначення |
|---|---|
| `products` | вітрина: ціна вже роздрібна, `cost_cents` зберігається для аудиту |
| `product_rejections` | відхилені ШІ товари з причиною |
| `ai_cache` | результати моделі за хешем контенту |
| `orders`, `order_items` | замовлення та статус по кожному постачальнику |
| `outbox` | листи постачальникам (черга/надіслано/помилка) |
| `sync_runs` | історія синків для `/v1/health` |
| `settings` | час останнього синку |

## iOS

- `RootView` обирає лейаут за `horizontalSizeClass`: iPad — `NavigationSplitView`
  (категорії зліва, каталог справа на весь екран), iPhone — `TabView` (Каталог, Кошик).
- `LazyVGrid(columns: [GridItem(.adaptive(minimum: 160))])` + пагінація по 24 при
  доскролі до останнього елемента.
- `CachedAsyncImage`: `NSCache` (400 зображень) + `URLCache` на 512 МБ на диску.
- Кошик — `CartStore` (`ObservableObject`), оформлення — форма з валідацією і
  `POST /v1/orders`. Жодних екранів оплати.

## Чому саме так

- **SQLite, а не Postgres**: один вузол, тисячі товарів, нуль адміністрування.
  `node:sqlite` дає синхронний API без нативних збірок — ідеально для CI.
- **Черга листів у БД**: якщо SMTP/API недоступний, замовлення не губиться.
- **Кеш ШІ за хешем**: повторний синк 6000 товарів не коштує нічого.
- **Окремі адаптери**: новий постачальник — це один файл і один рядок у `registry.js`.
